# Findings

Measured results from this pipeline. All data is synthetic, generated by `etl/pipeline.py` with a fixed random seed.

## Which model should decline risky loan applications: Random Forest or XGBoost?

**How it was tested.** Both models were trained on the same features and scored on the same held-out 20% of the synthetic loans.
Each declines every application it scores at 0.80 or more likely to default (`DECLINE_THRESHOLD` in `models/train.py`).
Both runs are logged to MLflow.

| Metric | Random Forest | XGBoost |
|---|---|---|
| ROC AUC | 0.9216 | 0.9179 |
| Accuracy | 0.8777 | 0.8801 |
| Decline precision | 0.9341 | 0.9132 |
| Decline recall | 0.3427 | 0.4456 |
| Share of applications declined | 0.0859 | 0.1143 |

**Decision.** The Random Forest goes to production: it has the higher ROC AUC and the higher precision when it declines an
application. XGBoost catches more defaults (recall 0.4456 against 0.3427) but declines more applications to do it.
`models/train.py` saves the Random Forest pipeline as `models/risk_model.pkl` for the API.

**Source.** `models/metrics.csv` (written by `models/train.py`).

## Which fraud rules can be trusted on their own?

**How it was tested.** Three rules in `etl/fraud_rules.py` flag card transactions from amount, time, location and customer only:
velocity (5 or more charges inside 10 minutes), amount spike (over 7 times the customer's median) and foreign location. Their
alerts were scored against the fraud the simulator planted, which the rules never read.

| Rule | Alerts | True fraud caught | Precision | Recall (all fraud) |
|---|---|---|---|---|
| Velocity | 1,110 | 1,110 | 1.0 | 0.4284 |
| Foreign location | 4,942 | 1,464 | 0.2962 | 0.565 |
| Amount spike | 4,069 | 40 | 0.0098 | 0.0154 |
| Any rule | 10,057 | 2,591 | 0.2576 | 1.0 |

**Decision.** The velocity rule is exact on this data: every alert is a planted card-testing charge. Amount spikes alone are
mostly legitimate large purchases, so they are kept as a review signal rather than a block. Together the three rules catch every
planted fraud case.

**Source.** `models/fraud_rule_metrics.csv` (written by `etl/fraud_rules.py`).

## Is the scoring API fast enough to sit in an application flow?

**How it was tested.** `POST /api/predict` was called 200 times on a laptop with the model loaded once and cached.
`tests/test_risk_api.py` fails the build if the median latency reaches 100 ms.

| Metric | Value |
|---|---|
| Median latency | 67 ms |
| 95th percentile latency | 85 ms |
| Build limit (median) | 100 ms |

**Decision.** The model is loaded once at startup and cached instead of per request, and the latency limit is enforced in CI.

**Source.** `README.md` (measured run), `tests/test_risk_api.py` (limit).
